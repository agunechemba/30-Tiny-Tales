Preface

Before We Begin

📖 Why thirty tiny tales

This book began with a question. A child looked up from a screen and asked, “But how does the computer know?” The honest answer — that it doesn't, unless someone tells it, step by step — was too long for bedtime. So it became thirty small stories instead.

Each tale takes one idea from the world of programming and dresses it in something familiar: a jigsaw puzzle, a robot's breakfast, a jar with a wax seal, a train of cake boxes, a calabash inside a calabash. None of the stories is a textbook. They are meant to be read aloud, one a night, and argued about at the dinner table.

The ideas, though, are the real ones — computational thinking, variables, loops, functions, arrays, recursion, debugging, optimization, HTML, JavaScript, Java applets. By the last page, the vocabulary of programming should feel less like a foreign language and more like a set of proverbs you already knew.

You do not need a computer to read this book. A pencil, some paper, and a willingness to ask “what if?” are enough. The Try It! sections at the end of each chapter are there to be done, not skipped — they are where the stories become yours.

If a single story makes you pause and say, “Oh — so that's what that means,” then the book has done its work.

— Agunechemba Ekene

Chapter 1

The Baobab Puzzle

🧩 Computational Thinking

Amara had a big puzzle. It had one thousand pieces! "I can't do this," she said. "It's too big!"

Mama sat with her. "Don't look at all the pieces. First, find the flat ones for the edge." Amara did. The big pile got small. That is breaking a big job into little jobs. Programmers call this problem-solving: the hardest part of programming is identifying all the little problems that make up the big problem. A computer is completely stupid, so you must tell it how to do everything — one small step at a time.

Then Amara saw that orange pieces are sky. Brown pieces are tree. Green pieces are leaves. She made little piles. That is seeing what is the same — grouping similar things together so you can handle them as a set instead of one by one.

"Do we need every leaf?" asked Mama. "No! Just the branches." That is keeping only what matters — ignoring unnecessary details so your plan stays simple and your instructions stay small.

Last, Amara made a plan: edge first, then sky, then tree, then leaves. That is a plan in steps — programmers call it a top-down design. By bedtime, the puzzle was done!

Big Idea

Big jobs are easy when you: break them into small jobs, see what is the same, keep only what matters, and go step by step. This is computational thinking — the problem-solving skill every programmer uses.

Try It!

Think of a big job, like cleaning your room. What small jobs can you do first? What is the same? What steps come first? Write your plan as a numbered list — that is your first program design.

Chapter 2

The Robot's Breakfast

🤖 Program, Instruction, Sequence

Tino the robot wanted fried plantain. "Fry the plantain," said Sade. Tino picked up the whole bunch and dropped it in the pot. Oil went everywhere!

"No, no," said Sade. "You need small steps. One at a time." A computer does nothing without someone telling it what to do, step by step. It cannot guess, and it cannot fill in gaps.

So Sade wrote:

1. Pick one plantain. 2. Peel it. 3. Cut it. 4. Heat the oil. 5. Fry it. 6. Add salt.

Tino did every step. Yum! But then Sade moved step 6 to the top. Tino put salt on a plantain that was not even peeled. Silly Tino!

"The order matters," said Sade. A list of steps in the right order is a program. Programmers call this sequential instruction — the computer follows instructions one after another, from the first instruction at the top to the last instruction at the bottom. If you change the order, the program does something different — or something silly.

Big Idea

A program is a list of small steps. The steps must be in the right order. Robots do just what you say — nothing more, nothing less. Sequential instructions are the simplest building block of every program.

Try It!

Tell a grown-up how to wash your hands in steps. Now say the steps in a silly order. What goes wrong? That is why programs need the right sequence.

Chapter 3

The Tongues of Babel

🗣️ Programming Languages

In the village of Babel, everyone spoke to computers. But no two people used the same tongue.

Old Man Machine spoke in zeros and ones: 0010 1010. The computer understood perfectly, but no human could read it. His grandson Assembly spoke in short commands — JMP, MOV, ADD — one command for many machine codes. Easier, but still tied to one processor.

Then came C, the portable assembler. C looked a little like English: printf("Hello!");. C could travel between computers, but it was dangerous — a careless C program could crash the whole machine. Next came the high-level languages: BASIC, Pascal, FORTRAN, COBOL. They looked even more like human language. PRINT "Hello!" was all BASIC needed. Easier to learn, safer to run, but slower.

As computers grew fancier, new tongues appeared. RAD languages like Visual Basic let you drag buttons onto a window. Database languages like SQL stored and retrieved information. Scripting languages like AppleScript and Revolution extended existing programs. Web languages like HTML, JavaScript, and Java made the Internet talk.

"Which tongue is best?" asked a child. "None," said the elder. "The best tongue is the one that solves your problem fastest. People argue about languages like they argue about colours — but a great BASIC programmer will always beat a mediocre C++ programmer."

Big Idea

Different languages exist for different jobs: assembly for speed, C for portability, BASIC for learning, SQL for databases, JavaScript for web pages. No single language is "best" — the right language depends on the task.

Try It!

Name a job for each tongue: Which language would you use to build a website? A database for a school? A game? A quick program to learn programming? There is no single right answer — but some fit better than others.

Chapter 4

Speaking Computer

🐢 Code, Statement, Syntax

A little tortoise lived on a hill. He only spoke computer. "Hello," said Ada. The tortoise said nothing.

So Ada learned his words. One line is one idea. She said hide() and the tortoise hid in his shell. She said walk(3) and he walked three steps. Each line is a statement. Programmers call each instruction a line of code, and the collection of all these lines saved in a file is called the source code.

But the tortoise was fussy. If Ada forgot a bracket, he sneezed. If she spelled a word wrong, he hiccuped. The fussy rules are called syntax. A syntax error happens when you type a command incorrectly — such as misspelling PRINT as PRINNT or forgetting a semicolon. The computer will not guess what you meant; it simply refuses to run the program.

"Why so fussy?" asked Ada. "Because," said the tortoise, "if I guess, I might do the wrong thing!"

Big Idea

Code is made of lines. Each line tells the computer one thing to do. The rules for writing it are called syntax. A single misspelling can stop the whole program from working.

Try It!

Say this sentence: "the cat sat the mat on." It sounds funny! Now fix it: "the cat sat on the mat." You just fixed syntax!

Chapter 5

The Plan Before the Build

📐 Program Design

The carpenter was about to build a chair. He picked up his saw. His apprentice said, "Wait! What kind of chair? Who will sit on it? Will it be indoors or outdoors?" The carpenter stopped.

Before writing any program, you must answer four questions: What problem does it solve? Who will use it? What computer will run it? and How skilled are you? If you can't state the problem clearly, you can't design the program.

The carpenter drew a picture first — a prototype. It showed what the chair would look like, but you couldn't sit on it yet. Programmers do the same: they mock up the user interface before writing any code. Then they write pseudocode — plain-English steps that show how the program will work, without worrying about syntax.

"Start at the top," said the carpenter. "The whole chair. Then the legs. Then the joints. Then the screws." That is top-down design: break the big problem into smaller and smaller pieces until each piece is clear.

Wise programmers never skip this step. Programs written without a plan become spaghetti — tangled, impossible to fix, and often abandoned. A program's life has three phases: development (building it), maintenance (fixing bugs as users find them), and upgrade (adding new features to sell the next version). Testing comes in two flavours: alpha testing (you test it yourself) and beta testing (strangers test it for you).

Big Idea

Plan before you build. Know the problem, the user, the target computer, and your own skill. Prototype the look, pseudocode the logic, and break the big job into small pieces. Programs written without a plan become spaghetti.

Try It!

Design a "Hello" program on paper. Who will use it? What computer will run it? What will the screen look like (prototype)? What steps will it follow (pseudocode)? Now you are ready to write it.

Chapter 6

The Toolbox and the Translator

🧰 Editors, Compilers, Interpreters

A programmer's workbench is full of tools. The first is the editor — a simple word processor where you type your source code and save it as a text file. No fancy fonts, no underlining — just characters.

The second tool is the translator, and there are three kinds. A compiler reads your entire program, converts it all into machine language, and saves the result in a separate file — often called an EXE. Do it once and you're done. An interpreter translates your program one line at a time and stores the result in memory. Every time you run the program, it must translate again. A p-code compiler is a hybrid: it translates your code into an intermediate form (byte code), and a special run-time program finishes the translation on each machine. Java is the most famous user of p-code.

The third tool is the debugger. It lets you step through your program line by line, set breakpoints to pause in specific places, and watch your variables change values. Without a debugger, finding bugs is like searching for a needle in a haystack.

Most compilers bundle editor, compiler, and debugger into one program called an IDE (integrated development environment). When your program is ready, you add two more tools: a Help-file creator (so users can find help on-screen) and an installation program (so users can copy your program to their computer without manual errors).

Big Idea

A programmer needs an editor to write, a compiler or interpreter to translate, and a debugger to fix. A compiler translates the whole program once; an interpreter translates one line at a time; p-code is a hybrid. An IDE combines all three.

Try It!

Imagine translating a whole book at once (compiler) versus translating a speech sentence by sentence live (interpreter). Which would be faster to read afterward? Which would be faster to start? Which would you prefer for a big project?

Chapter 7

In and Out

🚪 Input and Output

There was a doorbell at a shop. When you pressed it, it asked, "Who are you?" You said your name. It said, "Welcome, Zuri!"

Zuri thought about it all day. Pressing the button is something going in. The welcome is something coming out.

Later, Zuri made zobo. Flowers and water go in. Cold zobo comes out. The things going in are the input. The things coming out are the output.

Every program has a door for things going in and a door for things coming out. A program does nothing more than tell the computer how to accept some type of input, manipulate that input, and spit it back out in some form that humans find useful. A word processor takes the characters you type (input) and displays organized text (output). A game takes keystrokes (input) and moves a figure on-screen (output). A web browser takes HTML codes (input) and displays web pages (output). Input and output are the two doors every program needs.

Big Idea

Input is what you give the program. Output is what the program gives back. Every useful program has both doors: it accepts data, manipulates it, and produces a result.

Try It!

Look at a blender. What goes in? What comes out? Now try a toy car. What goes in? What comes out? Name the input and output for each.

Chapter 8

Boxes with Names

📦 Variables and Assignment

Grandpa had many boxes. Each box had a name on it. One said "millet." One said "groundnuts." One said "snacks."

"A box with a name is a variable," said Grandpa. "The name is the label. What is inside is the value." A variable acts like a box that can hold data, and it has a descriptive name so you can identify which variable to use. The computer handles the memory address for you; you only need to remember the name.

He put three mangoes in the box called "snacks." Then he took them out and put in a banana. "Where did the mangoes go?" asked Ada. "A box holds one thing," said Grandpa. "Put a new thing in, and the old thing is gone." A variable can store only one chunk of data at a time — the moment you put another chunk in, the variable dumps the old data and stores the new data. That is why we call it a variable: its contents can vary.

Ada made a box called "score." She put 0 in it. Then she won a game and put 10 in. Same box. New number! The act of putting a value into a variable is called assignment. In most languages you use the equal sign: score = 10 means "store the value 10 in the box named score."

Big Idea

A variable is a box with a name. It holds one thing at a time. When you put in something new, the old thing goes away. Choose descriptive names like FirstName or CustomerIDNumber so your code is easy to read.

Try It!

Draw three boxes. Name them "name," "age," and "score." Fill them in. Now change "score" to a bigger number. What happened to the old number? That is assignment in action.

Chapter 9

The Jar with a Seal

🫙 Constants

In the pantry stood a jar with a wax seal. On the seal was written: Interest Rate = 0.1975. Unlike the other jars, this one never changed its contents. It was a constant.

"What is the number 0.1975?" asked the child. "Without the seal," said the elder, "you would have to guess. Is it a tax? A score? The number of cats in the village? But with the seal, you know exactly what it means." A constant is a fixed value given a descriptive name — it makes the meaning of a number clear at a glance.

Later, the village changed the interest rate. The elder only had to break the seal on one jar and write the new number. "Why not just change the number everywhere it appears?" asked the child. "Because it appears twenty times in our records," said the elder. "Changing it once updates every copy. Changing it twenty times risks missing one." A constant lets you update a value in one place, no matter how large the program is.

Variables vary; constants don't. In C++ you write const double InterestRate = 0.1975;. In REALbasic, Const InterestRate = 0.1975. In Revolution, constant InterestRate = 0.1975. The jar stays sealed — until you choose to open it.

Big Idea

A constant is a fixed value with a descriptive name. It makes numbers meaningful and lets you update a value in one place instead of everywhere. Variables vary; constants don't.

Try It!

Look for a number in your life that always stays the same — your birth year, the number of legs on a spider, the boiling point of water. Give it a descriptive name. That is your first constant.

Chapter 10

Notes in the Margin

✏️ Comments

In the margins of an old book, a child found handwritten notes. They explained who wrote the book, when, and what each difficult passage meant. The book itself said one thing; the notes explained why.

Programmers write notes in the margins of their code. These notes are called comments. A comment might say who wrote the program, when it was created and last changed, what the program does, how it works, or any known problems. The computer ignores comments completely — they exist only for humans to read.

Different languages write comments differently. In Liberty BASIC: REM or an apostrophe '. In C++: // for one line or /* ... */ for several. In REALbasic: REM, ', or //. In Revolution: # or --. The style changes; the purpose stays the same.

Comments also have a clever trick. You can comment out a line — wrap it in comment symbols — to temporarily ignore it while testing. Instead of deleting a line and retyping it later, just hide it behind a comment.

But too many comments become a nuisance. The best comment is a clear piece of code. Write code so readable that it explains itself; then add comments only where the purpose is not obvious.

Big Idea

Comments are notes for humans, ignored by the computer. Use them to explain who, what, when, and why — or to temporarily hide lines of code. Write clear code first; add comments where they help.

Try It!

Write a sentence about what you did today. Now add a note in the margin explaining why you did it. That note is a comment. Now imagine hiding the sentence behind a comment so it doesn't appear — that is commenting out.

Chapter 11

Numbers, Words and Yes-or-No

🔢 Data Types

Three friends moved into the computer. Num loves numbers: 3, 42, 1000. Word loves letters: "hello," "jollof," "mango." Bool only says two things: true or false. He says them very loudly.

Someone asked, "What is 2 + 3?" Num said 5. Fast! Then Word tried. "Two plus three is… twenty-three!" Everyone stared. Word glued the numbers together!

"That is because you are a string," said Num. "You join letters. I am a number. I add." Bool nodded. "True," he said.

Each one has its own job. Numbers count. Strings are for words. Booleans answer yes or no. The three most common data types are whole numbers (integers like 3, 45, 102), decimal numbers (single- or double-precision like 3.1415), and text (strings like "hello"). Some languages add more types — a Boolean holds only True or False, a byte holds values 0–255, and a long holds extremely large integers.

Type-checking forces you to declare what type a variable holds so you never accidentally store a decimal in a whole-number box — which would be as silly as storing 1.48 children in a variable.

Big Idea

There are three basic types: numbers (3, 7.5), strings ("hi," "cat"), and Booleans (true, false). Each type has its own rules — a string joins, a number adds, a Boolean answers yes or no.

Try It!

Which is which? 12, "cat," true, "42," false, 3.5. Careful: "42" has quotes, so it is a string! The number 42 has no quotes, so it is an integer.

Chapter 12

The Math Magician

✨ Operators

The Math Magician had tiny wands. "Each wand does one trick," she said. "Only one."

She waved the adding wands. + puts numbers together. − takes away. * makes more. / shares out. Then the less-common wands: \ does integer division (25 \ 6 gives 4), mod gives the remainder (25 mod 6 gives 1), and ^ does exponentiation (2 ^ 3 = 8). She also carried built-in math functions — ABS for absolute value, SIN, COS, TAN, LOG, SQR — ready-made tricks for hard problems.

Then she showed the asking wands. > asks, "Is this bigger?" < asks, "Is this smaller?" == asks, "Are these the same?" >=, <=, and <> complete the family. These are relational operators — they always say yes or no.

Last were the yes/no wands. AND says yes only if both are yes. OR says yes if one is yes. NOT turns yes into no and no into yes. Cheeky NOT! These are Boolean operators.

One more secret: the Magician follows a strict order. Exponentiation first, then multiplication and division, then integer division and modulo, then addition and subtraction. Use parentheses to force a different order: 3 + 4 ^ 5 is 1027, but (3 + 4) ^ 5 is 16807.

Big Idea

Some wands do math: + − * / \ mod ^. Some ask questions: > < == >= <= <>. Some join yes and no: AND, OR, NOT. Parentheses always win — they force the computer to calculate inside them first.

Try It!

Say yes or no: Is 5 bigger than 3? Is 2 bigger than 7? Is "yes AND no" true? What about "NOT no"? Now try: what is 3 + 4 * 2? (Hint: multiplication before addition — the answer is 11, not 14!)

Chapter 13

The Alphabet Soup

🍜 Strings and Text Processing

In the soup lived a string named "jambo." It was not a word. It was beads on a line: j, a, m, b, o.

The string could tell you its length: five beads. It could show you bead 1: "a." It could shout "JAMBO!" or whisper "jambo." A string is anything you can type from the keyboard — letters, symbols, and even numbers. That is why "555-1212" in quotes is a string, while 555-1212 without quotes is the number -657. The quotation marks tell the computer "this is text, not math."

One day "nyama" met "choma." They hugged and became "nyamachoma." That is joining, also called concatenation. Some languages use + to join strings; others use & or special commands. Watch out: if you forget the space, you get "helloworld" instead of "hello world."

"Text is just letters in a row," said the spoon. Programs convert strings to numbers with functions like VAL (so you can do math on input the user typed) and numbers to strings with functions like STR$ (so you can display results). A computer treats the number 53 and the string "53" as completely different — as different as a real cat and a picture of a cat.

Big Idea

A string is text — letters in a row. You can count it, find a letter, make it loud, and join strings together. But "53" (a string) and 53 (a number) are not the same thing.

Try It!

Write your name. Count the letters. Now write it in CAPITALS. Now write it backwards, one letter at a time. Now join your name to a friend's name — what is the result?

Chapter 14

If It Rains

🌦️ Conditionals and Branching

Every morning Zainab looked at the sky. If it rained, she took an umbrella. If it was sunny, she took sunglasses. Then she went to school.

"You are using a conditional," said Mum. "Your day splits like a road. If it rains, go this way. Else, go that way." Programmers call this a branching statement. The simplest is the IF-THEN statement: if a Boolean expression is true, run one set of instructions; otherwise, skip them. Add an ELSE and the computer is forced to follow one path or the other.

Zainab saw forks everywhere. At the traffic light: if green, walk. Else, wait. In her game: if score is 100, you win. Else, keep playing.

Sometimes there are three roads: if rain, umbrella. Else if cold, scarf. Else, sunglasses. This is an IF-THEN-ELSEIF statement. When there are many exact values to check, programmers use a SELECT CASE (or switch) statement instead of a long chain of IFs.

"The computer is not clever," said Mum. "It just checks the question and takes the right road." That question is a Boolean expression — something either true or false, like (4 < 54) or (score == 100).

Big Idea

If something is true, do this. Else, do that. This is called a conditional. Programs use conditionals to react to data — without them, a program does the same thing every time no matter what.

Try It!

Make an if/else for a traffic light. If green, what? If red, what? What about yellow? Now make it an if/elseif/else with three roads.

Chapter 15

The Hundred Tiles

🔁 Loops and Iteration

The yard had one hundred stones. All were muddy. Sani washed stone one. Then stone two. Then stone three. He was very tired!

Grandma showed him a trick. "Say this: Repeat one hundred times: wash a stone and move on." Sani said it once. The stones got clean, one by one!

"That is a loop," said Grandma. "A for loop is when you know how many times. You give it a counter, a start value, an end value, and a step. It counts from start to end, repeating the instructions each time." Loops save you from typing nearly identical instructions over and over — a FOR-NEXT loop can print five numbers as easily as five million.

"A while loop is when you repeat until something stops — like: while the yard is muddy, keep washing." A WHILE loop repeats while a Boolean expression remains true; an UNTIL loop repeats until a Boolean expression becomes true. Both need a condition that will eventually change — otherwise you get an endless loop and the program freezes forever.

Sani looked at his food. While there is food, take a bite. He had been looping all his life!

Big Idea

A loop repeats things. Use for when you know the count. Use while when you wait for something to stop. Always make sure the loop can end — initialize the condition outside the loop and modify it inside.

Try It!

Find the loop in these: eating a bowl of rice, walking up ten steps, singing "Happy Birthday." Which one is a for loop? (Hint: walking up ten steps — you know the count!)

Chapter 16

The Helpers

👥 Subprograms and Functions

A big family lived in a house. Every morning there was chaos — everyone did every chore themselves. Breakfast took all day! Then the family hired helpers: one made chapati, one said hello to visitors, one swept the yard. Now each helper did one job. Breakfast took one hour.

Programmers do the same. They divide a large program into smaller parts called subprograms. A subprogram is a small program that solves a single task — like verifying a password or multiplying two numbers. The main program simply calls each helper when needed. The main program stays small; the helpers stay focused.

There are two kinds of helpers. A procedure just does a job and returns nothing — like the helper who sweeps the yard. A function does a job and gives something back — like the helper who makes chapati and hands you a plate. A function accepts data, performs a calculation, and returns a single result. You can assign that result to a variable or use it inside a formula: Angle = cos(0.75).

Subprograms accept data through a parameter list. Each parameter is a slot; the actual value you pass in is an argument. The helper who makes chapati needs flour — flour is the parameter; the cup you hand over is the argument. When you call a function, the answer it gives back is its return value.

Why bother? Because subprograms let you write once, use many times. They make programs easier to read, easier to fix, and easier to share with other programmers. Each helper does one job well — and the whole household runs smoothly.

Big Idea

A subprogram is a small program that solves one task. A procedure does a job; a function does a job and returns a value. Parameters are the slots; arguments are what you put in. Subprograms make big programs manageable.

Try It!

Make a function called makeChapati(flour). What goes in the slot? What comes out? Now make greet(name). What is the parameter? What is the return value? Now make a procedure called sweepYard() — does it return anything?

Chapter 17

The Borrowed Toolbox

🧰 Libraries and APIs

Nneka wanted to build a stool. First she made a hammer from a stone and a stick. It took all morning. It was a bad hammer.

"Why not use the toolbox?" asked her neighbour. Inside were hammers and saws that other people made. "A library is a toolbox of code. You borrow a tool and get on with your job." A library is a collection of tested subprograms stored in a separate file. Instead of writing every function yourself, you tell your program to include the library and then use its functions. That is what C++ does with #include <iostream.h> — it grabs a toolbox of input and output routines. Libraries save time, and tested library code is less likely to contain bugs than code you just wrote.

Later Nneka needed wood. She did not cut a tree. She went to the timber yard and asked for a plank. "That is an API," said her neighbour. "A friendly counter. You ask the right way, you get an answer." An API (Application Programming Interface) is the set of rules for talking to someone else's code: the names of the functions, what parameters they expect, and what they return. You do not need to know how the timber yard cuts the wood — you only need to know how to ask.

Nneka finished the stool before lunch! By dividing a large program into smaller subprograms stored in separate files, programmers keep their main program small, reuse code across projects, and let different people work on different parts at the same time.

Big Idea

A library is code someone else made. You can use it. An API is the way you ask for something and get it back. Both save you from reinventing the hammer every morning.

Try It!

Name three real-life libraries: a recipe book, a spell-checker, a map app. What does each one save you from doing? For each one, what is the "API" — how do you ask it for help?

Chapter 18

The Train of Puff-Puffs

🚂 Arrays

Baker Bisi made a train from cake boxes. Each box held one puff-puff. Each box had a number. Box 0 held plain. Box 1 held coconut. Box 2 held ginger.

"Why does the first box have 0?" asked her helper. "Because computers count from zero!" said Bisi. "The number is the index. What is inside is the element." An array is a single variable name that can hold a list of data — but every element must be the same data type. Arrays that start counting from 0 are called zero-based arrays; some languages start at 1 and call them one-based arrays.

She counted: three boxes. "That is the length." When a new puff-puff came, she added a box. When one was eaten, the boxes moved up. A dynamic array can grow or shrink while the program runs; a static array has a fixed size you declare once and cannot change.

A train of things in order is called a list or an array. Arrays save you from creating dozens of nearly identical variables like Name1, Name2, Name3 — instead you create one array and use a loop to store and retrieve items. When you need a grid of data, you can make a two-dimensional array; when you need even more, you can make three-, four-, or nine-dimensional arrays (though most programmers stick to one or two).

Big Idea

A list holds many things in order. Each thing is an element. Its place is the index. The number of things is the length. In most languages, the first index is 0, not 1 — watch out for off-by-one mistakes!

Try It!

Make a list of five friends. Who is at 0? Who is at 4? How many friends in all? (Hint: if you count 0, 1, 2, 3, 4, that is five friends.) Now try making a two-dimensional array — a grid of rows and columns.

Chapter 19

Inside the Treehouse

🌳 Scope and Lifetime

Kofi built a treehouse. It had a secret password, a mat, and a tin of groundnuts. Everything inside was only for the treehouse. The password only worked inside. Shout it outside and nothing happened.

"Those are local things," said Dad. "They live in one place." A local variable is one declared inside a subprogram or function; only that subprogram can see it. This is a form of isolation — the same principle behind encapsulation in object-oriented programming, where objects keep their data and the instructions that manipulate that data together, away from the rest of the program.

He pointed at the sun. "The sun is global. Everyone can see it." A global variable is declared outside any subprogram, so every part of the program can read and change it.

One more rule: when the treehouse was packed away, the groundnuts went with it. Local things go away when their place goes away. That is their lifetime. When a subprogram finishes running, its local variables are destroyed and their memory is freed. Global variables last as long as the program runs.

"So a variable inside a function," said Kofi, "is a groundnut in a treehouse." "Exactly," said Dad. And just as one subprogram's data should not be messed up by another subprogram's instructions, good programmers keep their variables as local as possible to avoid accidental interference.

Big Idea

Local things live in one place and disappear when that place goes away. Global things are everywhere and last as long as the program. Lifetime is how long a thing lasts; scope is where it can be seen.

Try It!

Local or global? Your name inside a "say hello" function? The sun? A loop counter? The year? (Answers: local, global, local, global.)

Chapter 20

The Chin-Chin Cutter Family

🥟 Object-Oriented Basics

In the kitchen drawer lived a star-shaped chin-chin cutter. It was not a chin-chin. It was the idea of a chin-chin. That is a class. A class defines the data stored in an object along with the instructions that manipulate that data — it is a blueprint, not the thing itself. Press it into dough and you get a real star chin-chin. That is an object. You can create many objects from one class, just as one cutter can make many chin-chin.

Each chin-chin was different. One was golden. One was brown. One had a missing corner. Those are its properties (also called data). In a class, properties are the variables that describe what each object is like — its colour, its size, its position, its name.

Each chin-chin could do things. It could be decorated. It could be eaten. Things an object can do are its methods — the subprograms stored inside the object that manipulate its properties. Keeping data and methods together in one place is called encapsulation. It stops one part of a program from accidentally messing with another part's data.

One day a new cutter came. It was a star with a little cap on top. It was made from the star cutter and just added a cap. "That is inheritance," said the big cutter. "It got everything from me, and then a cap." Inheritance lets a new class reuse all the properties and methods of an existing class without physically copying the code — and you can add new features or rewrite existing methods (which is called polymorphism) without touching the original class.

One cutter, many chin-chin. Same recipe, each one its own little self. That is the magic of object-oriented programming: define the blueprint once, then stamp out as many independent objects as you need — each with its own data, all sharing the same design.

Big Idea

A class is a plan. An object is one thing made from the plan. Objects have properties (what they are) and methods (what they do). Inheritance lets a new class build on an old one. Encapsulation keeps each object's data safe from the rest of the program.

Try It!

Make a class called Pet. What properties does it have? Name, colour, legs? What methods? Speak, eat, sleep? Now make two pets. They share the same blueprint but have different names and colours — that is the difference between a class and an object.

Chapter 21

The Lost Cowrie

🔍 Searching and Sorting

A cowrie hid in one of one hundred calabashes. "Guess," said Grandpa. "Number 1? No. Number 2? No." That could take all day! That is a sequential search: you examine every possible item until you find what you're looking for. It works on sorted and unsorted lists, but for large amounts of data it is slow and cumbersome — like looking for your car keys somewhere in the city of New York.

"Let me try," said Kwame. "Is it in 1 to 50?" No. "51 to 75?" No. "76 to 88?" Yes! Each question cut the work in half. Kwame found it in seven guesses. That is binary search. A binary search divides a long (previously sorted) list in half, checks the middle, and discards the half that cannot contain the target. Seven guesses is enough for 100 items because 2⁷ = 128. But binary search has one strict rule: the list must already be sorted.

Then Grandpa spilled numbered cards. Kwame picked them up and put each one in its place. "That is sorting," said Grandpa. "Putting things in order." There are many sorting algorithms: insertion sort (good for small lists), bubble sort (good when the list is almost sorted), shell sort (a divide-and-conquer speed-up), and quicksort (usually fastest for everyday use). Choosing the right one can make a program run quickly; choosing the wrong one can make it seem unbearably slow.

"An algorithm is a plan," said Kwame. "And efficiency is using few steps." Computer scientists measure efficiency with Big-O notation — a way to express how an algorithm's speed grows as the number of items grows. "Yes," said Grandpa. "Fewer steps means more time for chin-chin!"

Big Idea

An algorithm is a step-by-step plan. Searching finds one thing. Sorting puts things in order. Few steps is better than many steps — and Big-O notation lets us measure just how few.

Try It!

Play guess-the-number from 1 to 100. Cut the numbers in half each time. Can you win in seven guesses? (Yes — if you always guess the middle of the remaining range.)

Chapter 22

The Calabash Inside the Calabash

🏺 Recursion

Aisha opened a big calabash. Inside was a smaller one. She opened that one. Inside was a smaller one still! And inside that one — another!

"How many are there?" she asked. Grandma said, "Open one, then ask the one inside. It will ask the one inside it." Aisha laughed. "But that never stops!"

"It stops," said Grandma, "because the tiniest calabash does not open. It just says 'one.' That is the base case." A base case is the one situation where the function does not call itself — it simply returns a fixed answer. Without it, the function would keep calling itself forever and the program would crash.

So the big one said "one plus what is inside." The next said the same. Until the tiny one said "one." Then the answers ran back up. A function that calls itself is called recursion. Recursion is used in algorithms like quicksort, where a subprogram repeatedly runs itself on smaller and smaller pieces of the same problem. The pattern is always the same: a recursive case that breaks the problem into a smaller copy of itself, and a base case that stops the chain.

Big Idea

Recursion is when something calls itself. It always needs a base case so it can stop — otherwise it runs forever, like a calabash that never bottoms out.

Try It!

Count down out loud: "3, then count from 2, then count from 1, then count from 0 — stop!" Which part was the base case? (Counting from 0: stop.) Which part was the recursive case? (Counting from any number greater than 0: "count from one less.")

Chapter 23

The Wobbly Bug

🐛 Bugs and Debugging

Chidi made a game. A little goat runs on the screen. But when he pressed play, the goat ran backwards and fell off! "It's broken!" he cried.

His sister looked. "You have a bug. A bug is one little mistake. Let's find it." A bug is any problem that keeps a program from working correctly. Bugs fall into three families: syntax errors (typos and missing punctuation), run-time errors (the program crashes when it meets unexpected data), and logic errors (the program runs but does the wrong thing).

They played the game again. The goat fell off every time. Good! A bug you can see again is easy to catch. This is called testing boundary conditions — trying extremely high and extremely low values to see what breaks.

They looked at the lines. There it was! A minus sign where a plus sign should be — a logic error. They fixed it. The goat ran the right way!

"Fixing a bug is called debugging," said his sister. "Then you play again to be sure." The best debugging tools are stepping (running the program line by line), breakpoints (stopping at a chosen line), and watching (checking a variable's value as the program runs). No program is ever 100 percent bug-free — but debugging makes it good enough for people to actually use.

Big Idea

A bug is a mistake. To fix it: make it happen again, find it, fix it, and test again. Bugs come in three families — syntax, run-time, and logic. Programs rarely work perfectly the first time.

Try It!

Here is a silly recipe: "Put water in the cup. Get a cup. Drink." What is wrong? What should come first? That is a logic error — the steps work, but they are in the wrong order.

Chapter 24

The Tester's Tea Party

🫖 Testing

Temi made clay teacups. "They are done!" she said. "How do you know?" asked her aunt. Temi blinked. She had not checked!

So Temi tested them. She poured in hot tea. She poured in cold tea. She filled one to the top. She held one upside down. She even gave one to the goat!

One cup leaked. One handle broke. Temi wrote down each problem and fixed it. Then she tested again.

"Testing is checking what really happens," said her aunt. "Test the normal things. Then test the silly things." Programmers call this testing boundary conditions: give your program extremely high and extremely low numbers. If your program expects a person's age, try 0, try a huge number like 60,000, and try a negative number. That is how you smoke out run-time errors before real users find them.

Professional programmers go further. During alpha testing, you test your own program. During beta testing, you give copies to strangers so they can find bugs your friends are too polite to mention. No program is ever 100 percent bug-free — mathematics makes that impossible — but testing makes it good enough for people to actually use.

Big Idea

Testing means checking your work. Try normal things, big things, and silly things. A slow, bloated program that works is better than a small, fast program that doesn't.

Try It!

Imagine a machine that adds numbers. What should it do with 0 + 0? With 99 + 1? With 5 + 3? Guess first, then check. What happens if you give it letters instead of numbers?

Chapter 25

The Rickshaw Tune-Up

🛺 Optimization

A rickshaw driver finished his work. The rickshaw worked — but it was slow, heavy, and gulped petrol. "It works!" he said. "Why tune it?" His friend, a mechanic, laughed. "Because a slow rickshaw that works is worse than a fast one that works just as well."

Optimization means making a program faster, smaller, and less memory-hungry — without breaking it. The first step is choosing the right data structure: a dynamic array that grows as needed wastes less memory than a giant static array mostly filled with empty space. The second step is choosing the right algorithm: quicksort sorts 30,000 names much faster than bubble sort; binary search finds a name much faster than sequential search (but only if the list is sorted first).

The third step is fine-tuning the source code. Put the condition most likely to be false first in an AND expression — if the first is false, the computer skips checking the second. Put the condition most likely to be true first in an IF-ELSEIF or SELECT CASE statement — the computer finds a match sooner. Don't use a FOR-NEXT loop when a WHILE loop can stop early. Remove instructions from loops that don't need to repeat. Use the smallest data type that fits your values. Use built-in commands whenever possible.

Finally, you can use a faster language (C++ runs faster than BASIC) or optimize your compiler (turn on speed settings, though some turn off error-checking). But remember: a slow, bloated program that works is better than a small, fast one that doesn't. Optimize after it works, not before.

Big Idea

Optimization makes a working program faster, smaller, and leaner. Choose the right data structure and algorithm. Fine-tune your source code. Use built-in commands. But never optimize a program that doesn't work yet.

Try It!

Imagine searching for a word in a dictionary. Do you start at page 1 and read every page (sequential search), or do you open to the middle and flip left or right (binary search)? Which is faster? Now imagine the dictionary is unsorted — which search can you still use?

Chapter 26

The Shop Counter and the Bell

🔔 User Interface and Events

A shop had a plain counter with a sign: "Type what you want." Customers typed letters and sometimes made spelling mistakes. If they typed the wrong word, the counter did nothing to help. That is a command-line interface — old-fashioned, fussy, and easy to get wrong.

Then the shopkeeper redesigned the counter. Now there was a window with buttons ("Buy," "Sell"), check boxes ("Gift wrap?"), radio buttons ("Small / Medium / Large" — pick one), list boxes (choose a flavour), combo boxes (pick or type), and text boxes (type your name). Pull-down menus at the top let you pick a command. That is a graphical user interface — friendly, visual, and hard to get wrong.

On the door hung a bell. When a customer opened the door, the bell rang. The shopkeeper looked up and said, "Welcome!" The ring is an event; what the shopkeeper does is the event handler. Programs have bells too: a mouse click (onClick), a key press (onKeyPress), a focus change (onFocus, onBlur), a text change (onChange), a mouse-over (onMouseOver), a mouse-out (onMouseOut), and a text selection (onSelect).

Waiting for something to happen is called being event-driven. Instead of running a fixed list of steps from top to bottom once, the program sits and waits, then responds to whatever the user does. That is how every modern app works — buttons, menus, check boxes, and text fields all wait for their events.

In REALbasic and Revolution, you design the interface by dragging controls onto a window and then write subprograms that run when events happen. In Liberty BASIC and C++, you write code to create every button, menu, and box — more work, but the same idea: the interface is the middleman between the user and the program.

Big Idea

A user interface is how the user talks to the program. A GUI uses windows, menus, and controls (buttons, check boxes, radio buttons, list boxes, text boxes). An event is something that happens; an event handler is what the program does in response. Programs that wait for events are called event-driven.

Try It!

Look at a game or app you use. Name three events (touch, click, key press) and what happens when each occurs. What is the "bell"? What is the "handler"? Now design a simple window with three controls — a text box, a check box, and a button.

Chapter 27

The Backpack, the Line and the Plates

🎒 Data Structures

Four friends carried things in different ways.

Map had a backpack with named pockets. "Pencils" went in one. "Snack" went in another. You asked for a pocket by name. Quick! That is a dictionary (also called an associative array). Instead of looking things up by number, you look them up by key. Choosing the right data structure matters: a map is fast when you know the name of what you want, but wasteful if you just need an ordered list.

Set had a bag with a rule: no two the same. Two red marbles? Only one went in. "I just want to know if it is in there," said Set. Sets are perfect for membership tests and for removing duplicates.

Stack carried plates. You put one on top. You take one off the top. Last in, first out (LIFO). The undo button in a program is a stack: the most recent action is the first one undone.

Queue stood in a line at the tap. First in, first out (FIFO). "Good for taking turns," said Queue. A printer queue works this way: the first job sent is the first job printed. Choosing the wrong data structure can make a working program slow and memory-hungry — the right one makes it fast and lean.

Big Idea

A map looks things up by name. A set has no duplicates. A stack is last in, first out. A queue is first in, first out. Each structure is a different tool for a different job.

Try It!

Which is which? The undo button (stack). Jobs waiting for a printer (queue). A phone book (map). A list of people who already voted (set — no one votes twice).

Chapter 28

The Painted Signboard

🪧 HTML

A signboard painter had a strange rule. Every mark he made had to be wrapped in brackets. <b> for bold. <i> for italic. <h1> for a big heading. Most marks came in pairs: <b>bold</b>. The second bracket had a slash — that meant "stop." These brackets are called tags, and the language they make is HTML (HyperText Markup Language).

Every signboard had the same skeleton: <HTML> at the top and bottom, <HEAD> for the title, <BODY> for everything you actually see. Inside the body, the painter used headings <H1> through <H6>, paragraphs <P>, quotes <BLOCKQUOTE>, bold <B>, italic <I>, underline <U>, typewriter <TT>, and horizontal rules <HR>.

He could add attributes inside the first tag to change how things looked. ALIGN="center" centred the text. BGCOLOR="white" painted the background. TEXT="black" set the text colour. LINK and VLINK coloured hyperlinks (visited and unvisited).

He could make three kinds of lists: unordered <UL> with bullets, ordered <OL> with numbers, and definition <DL> with indented terms and definitions. He could make hyperlinks with <A HREF="...">click me</A> to jump to another page, or <A NAME="..."> to anchor a spot on the same page. He could display pictures with <IMG SRC="...">, align text next to pictures with ALIGN, and paint a background picture with BACKGROUND="...".

And when he wanted to ask the visitor something, he painted a form with <FORM>: text boxes for typing TYPE="text", buttons for clicking TYPE="button", check boxes for ticking TYPE="checkbox", and radio buttons for choosing one TYPE="radio". Every control could have an event like onClick — the same bells and handlers from the last chapter, now painted on a signboard.

Big Idea

HTML wraps content in tags. Most tags come in pairs: an opening tag and a closing tag with a slash. Tags can carry attributes that change appearance. HTML can make headings, paragraphs, lists, hyperlinks, images, and forms — the building blocks of every web page.

Try It!

Write a tiny HTML page on paper. Use <HTML>, <HEAD><TITLE>, <BODY>, one heading, one paragraph, one bold word, and one list. Then try it in a real editor and save it as .html — open it in a browser to see your signboard.

Chapter 29

The Talking Signboard

💬 JavaScript

The painted signboard from Chapter 28 was pretty, but it could not talk back. It showed the same thing to everyone. Then a clever painter added a small script box: <script language="JavaScript">. Now the signboard could think.

Inside the script box, the painter could write document.write("Hello!") to paint text onto the page. He could make variables with var mymessage and join strings with +. He could make dialog boxes: an alert() to shout a warning, a confirm() to ask a yes-or-no question, and a prompt() to ask for input and store it in a variable.

He could make functions — small subprograms that accept data and return a result, just like Femi the Function. function square(number) { return number * number } doubles a number with one line. He could open windows with window.open("index.html"), decide their size and whether they show toolbars, and close them with windowName.close().

And he could attach scripts to events: onClick, onChange, onFocus, onBlur, onMouseOver. When the user clicked a button, the script ran. The bell rang; the handler answered. The signboard was no longer just painted — it was alive.

Big Idea

JavaScript makes web pages interactive. It can display text, store variables, show dialog boxes, define functions, open and close windows, and respond to events. It is the language of the talking signboard.

Try It!

Write a JavaScript function called greet(name) that displays "Hello, [name]!" using alert(). Attach it to a button with onClick. Now you have a talking signboard.

Chapter 30

The Applet in the Window

🪟 Java Applets

Inside the talking signboard, the painter sometimes hung a tiny window. Inside the window lived a little clock, or a game, or an animation. That little window is an applet — a miniature program written in Java that runs inside a web browser.

Java works differently from C++. C++ compiles a program directly into machine code for one processor. Java compiles a program into byte code — a kind of universal machine language. To run byte code, the computer needs a special program called the Java Virtual Machine (VM). Install the VM on Windows, Mac, or Linux, and the same byte code runs on all of them without changes. That is Java's promise: write once, run anywhere.

To hang an applet in a web page, the painter used <APPLET CODE="Message.class">. He could set the size with WIDTH=300 HEIGHT=180. He could align text with ALIGN=top, ALIGN=middle, or ALIGN=bottom. He could push text away with HSPACE (horizontal space) and VSPACE (vertical space). And he could put fallback text between the opening and closing tags — text that appeared only if the browser could not run Java.

Java and JavaScript are not the same. JavaScript is easy, lives inside the browser, and handles small tasks. Java is more powerful, runs on its own VM, and handles big ones. Use JavaScript for a quick button response; use Java for a full-blown animation. Use both together and you get the best of both worlds.

Big Idea

A Java applet is a miniature Java program that runs inside a web browser. Java compiles to byte code and runs on any computer with a Java Virtual Machine. Use <APPLET> tags to add one to a page. JavaScript is smaller and simpler; Java is more powerful.

Try It!

Compare two tasks: changing a button's colour when clicked (JavaScript) versus drawing a moving clock on the page (Java applet). Which language fits which task? Now imagine writing <APPLET CODE="Clock.class" WIDTH=200 HEIGHT=100 HSPACE=10 VSPACE=10>. What would you see on the page?

Appendix

Key Terms

📚 A glossary of the ideas in this book

Algorithm — A step-by-step plan for solving a problem; the recipe a computer follows.

API (Application Programming Interface) — The agreed set of names, inputs, and outputs for asking someone else's code to do something for you.

Argument — The actual value you pass into a subprogram when you call it; it fills one of the parameters.

Array — One variable that holds a list of items of the same data type, each reached by its index.

Assignment — Putting a value into a variable, usually written with an equals sign: score = 10.

Base case — The stopping condition of a recursive function; the smallest case that returns an answer without calling itself again.

Beta testing — Giving a nearly finished program to strangers so they can find the bugs your friends are too polite to mention.

Binary search — Finding an item in a sorted list by halving the range again and again; fast, but only on sorted data.

Boolean — A data type with exactly two possible values: true or false.

Bug — A mistake in a program that makes it crash, freeze, or do the wrong thing.

Byte code — A universal intermediate language produced by the Java compiler and run by the Java Virtual Machine on any computer.

Class — A blueprint describing the data (properties) and behaviour (methods) shared by a kind of object.

Compiler — A tool that translates the whole program into machine code once and saves it as a separate runnable file.

Computational thinking — Solving big problems by breaking them into small ones, spotting what is the same, ignoring what doesn't matter, and planning in steps.

Constant — A named value that never changes while the program runs.

Data structure — A way of organising data — array, map, set, stack, queue — chosen to suit the job.

Data type — The kind of value a variable holds: number, string, Boolean, and so on.

Debugger — A tool that lets you step through a program line by line, pause at breakpoints, and watch variables change.

Debugging — The work of finding and fixing bugs.

Declaration — The statement that introduces a variable or constant and gives its name and type.

Editor — The plain-text tool where you type and save source code.

Element — One item inside an array or list.

Encapsulation — Keeping an object's data and the methods that manipulate it together, safe from the rest of the program.

Event — Something that happens while a program runs: a click, a key press, a page finishing loading.

Event handler — The piece of code that runs in response to an event.

Expression — A combination of values, variables, and operators that produces a new value.

Function — A subprogram that performs a task and returns a value.

Global variable — A variable declared outside every subprogram, visible to the whole program and alive for as long as it runs.

GUI (Graphical User Interface) — A user interface built from windows, menus, buttons, check boxes, and other visual controls.

HTML (HyperText Markup Language) — The tag language that describes the structure and appearance of a web page.

IDE (Integrated Development Environment) — A single program that bundles an editor, a compiler or interpreter, and a debugger.

Index — The position number of an element in an array; in most languages the first index is 0.

Inheritance — Building a new class on an existing one, reusing its properties and methods and adding or changing only what is different.

Input — Data that goes into a program: keystrokes, clicks, a file, a sensor reading.

Interpreter — A tool that translates and runs a program one line at a time, and must do it again every time the program runs.

Iteration — Repeating a set of instructions; looping.

JavaScript — The scripting language that makes web pages interactive inside the browser.

Library — A collection of ready-made, tested subprograms stored in a separate file and reused in your program.

Lifetime — How long a variable exists in memory, from the moment it is created to the moment it is destroyed.

Local variable — A variable declared inside a subprogram, visible only there, and destroyed when the subprogram ends.

Logic error — A bug where the program runs without crashing but does the wrong thing.

Loop — A structure that repeats instructions: for when you know the count, while or until when a condition decides.

Method — A subprogram that belongs to an object and works on that object's data.

Object — One concrete thing made from a class, with its own copy of the data.

Object-oriented programming — Organising a program around classes and objects, using encapsulation, inheritance, and polymorphism.

Operator — A symbol that performs an action: + − * / for arithmetic, > < == for comparison, AND OR NOT for logic.

Output — The result a program gives back to the user.

Parameter — A named slot in a subprogram's definition that receives a value when the subprogram is called.

p-code — Intermediate code produced by a hybrid compiler and finished by a run-time program on each machine; Java's byte code is the famous example.

Polymorphism — Redefining a method in a subclass so the same name behaves differently for different objects.

Procedure — A subprogram that performs a task but returns no value.

Program — An ordered list of instructions that tells a computer what to do.

Programming language — A formal language for writing instructions a computer can execute.

Pseudocode — Plain-English steps that describe a program's logic before any real syntax is written.

Queue — A first-in, first-out data structure; like a line at the tap.

Recursion — A subprogram calling itself on a smaller version of the same problem until a base case stops it.

Return value — The result a function hands back to whoever called it.

Run-time error — A bug that makes the program crash while it is running.

Scope — The part of a program where a variable's name can be seen and used.

Sequential search — Checking every item in turn until you find the one you want; works on unsorted data, but slowly.

Set — A collection that never holds duplicates.

Sorting — Arranging data in order so that it can be searched, read, and used efficiently.

Source code — The text of a program as the programmer wrote it, before translation.

Stack — A last-in, first-out data structure; like a pile of plates, or the undo button.

Statement — A single instruction in a program, usually written on one line.

String — A sequence of characters treated as text; "53" is a string, 53 is a number.

Subprogram — A small named program that solves one task and can be called from elsewhere; either a procedure or a function.

Syntax — The grammar rules of a programming language.

Syntax error — A mistake in spelling or punctuation that stops a program from running at all.

Testing — Checking what a program actually does, with normal values, extreme values, and silly values.

Top-down design — Breaking a big problem into smaller and smaller pieces until each piece is simple enough to write.

Two-dimensional array — An array of arrays; a grid of rows and columns.

Variable — A named box in memory that holds one value at a time, and whose contents can change.

Big Idea

Programming is a vocabulary as much as a skill. Learn the words, and the machine stops being a mystery — it becomes a thing you can describe, and therefore a thing you can command.
